你说的两个问题——**板块划分不合理**、**总觉得漏解法**——是同一个根因：

### 修复 1：抽 which-key 分组（板块划分）

`nvim_get_keymap` 只给 lhs/desc/rhs，**拿不到 which-key 的分组**。
分组是 LazyVim 在 which-key 的 plugin opts 里注册的：

```lua
-- ~/.local/share/nvim/lazy/LazyVim/lua/lazyvim/plugins/editor.lua:68
spec = {
  { "<leader>b", group = "buffer" },
  { "<leader>c", group = "code" },
  { "<leader>f", group = "file/find" },
  ...
}
```

旧脚本没抽它，所以 `lib/bindings.ts` 里那 20 个 `group` 是**手写前缀规则猜的**。

**踩的坑（值得记）**：which-key 的 `config.setup()` 里，消费 spec 的 `load()`
被 `vim.schedule_wrap` 延迟，而且 headless 下 `vim_did_enter == 0` 走的是
「注册 VimEnter autocmd」那条分支——脚本跑完时 `load()` 从没执行，
`Config.mappings` 是 0、`M.loaded` 是 false。

绕了四轮：先以为分组在 `_queue` 里（只有 6 条）→ 再以为 leader 没归一化
（改了还是 14 个键）→ 再试 `:WhichKey`（headless 下阻塞等输入，卡死）→
最后手动触发 `VimEnter` + `vim.wait` 等 `Config.loaded` 才成。

**结果**：`scripts/dump-maps.lua` → `data/keymaps.json`

```
387 键（rhs 158 / lua 229）· 分组定义 50 条 · 归组 222 键（57%）
```

真实分组条数（对比首页现在把「窗口」放第一，其实只有 2 条）：

| 分组 | 条数 | | 分组 | 条数 |
|---|---|---|---|---|
| search | 40 | | code | 10 |
| goto | 30 | | diagnostics/quickfix | 8 |
| ui | 24 | | quit/session | 5 |
| next / prev | 22 / 22 | | windows | 2 |
| git | 18 | | buffer | 10 |
| file/find | 14 | | | |

未归组的 165 条主要是顶层裸键（`<Space>` 单字母）、Vim 内建键、Insert/Visual 模式键。

### 修复 2：补回 rhs（解法判定）

旧 `extract.lua` 第 34 行**抽了 rhs**：

```lua
acc[#acc + 1] = { lhs = m.lhs, desc = m.desc or "", rhs = m.rhs or "" }
```

但第 52-57 行写 JSON 时**没带上它**——只写了 `mode` / `mode_desc` / `lhs` / `desc`。
抽出来又扔掉了。

后果：判定「是不是同一条命令」只能退而用 `desc`（插件描述文字），
于是手写表出错。实测对比：

| rhs | 真实等价键 | 旧手写表 |
|---|---|---|
| `<Cmd>BufferLineCycleNext<CR>` | `L` `]b` | `L` `]b` `<Space>bb` `<Space>b\`` ❌ |
| `<Cmd>BufferLineCyclePrev<CR>` | `H` `[b` | `H` `[b` `<Space>b\`` ❌ |
| `<Cmd>e #<CR>` | `` ` `` `<Space>bb` | 未收录 ❌ |
| `v:count == 0 ? 'gj' : 'j'` | `j` `<Down>` | 未收录 ❌ |
| `v:count == 0 ? 'gk' : 'k'` | `k` `<Up>` | 未收录 ❌ |

**手写表既多又少**：把 `<Space>bb` 当成 `L` 的等价解（其实它是 `` ` `` 的，
`:e #` 交替缓冲区），同时漏了 `j`/`<Down>`、`k`/`<Up>` 这两组。
这正是你「总觉得有漏掉的解法」的来源。

### 结论：一个命令 = 一道题 + 附属解法列表

你确认过：**只练最优解，其他解只做展示**。所以数据结构是：

```
Command {
  id           一个命令一道题
  display      最优解（用于出题，判分只认它）
  alternates   次解（实测等价）—— 仅展示
  native       原生 Ex —— 仅展示
}
```

不需要为每个等价解都出题，所以题量不翻倍。
368 个键 → 按命令聚合后是 **260 道题**，等价键挂在 `alternates` 上。

### 修复 3：重建数据集（阶段 1 已完成）

`scripts/build-dataset.mjs` 整个重写，产出 `lib/bindings.ts`：

```
368 个键 → 260 道题
  多解        13 道（13 个次解，仅展示）
  原生 Ex     86 道有，其中 77 条实测核实
  分组        18 个
```

**聚合踩的三个坑**（都是实测数据逼出来的）：

1. **`nvim_get_keymap("v")` 里真的有两条一模一样的 `<C-S>`** ——
   不去重会让它自己成为自己的次解，页面上显示「`<C-S>`，次解：`<C-S>`」。

2. **同一命令在 n/v/x 各注册一条是常态** ——
   `j`/`<Down>`/`k`/`<Up>` 的 rhs 是 `v:count == 0 ? 'gj' : 'j'`，
   在三个 mode 各有一条。我第一版把 mode 算进命令身份，
   于是「Up」出了 3 道题、「Down」出了 3 道题 —— 练同一件事练三遍。
   **去掉 mode 后合成一道**，mode 记在 `modes` 数组里。

3. **去重要在选最优解之前做** ——
   否则次解列表长成「次解：`<Up>` `<Up>` `k` `k` `k`」，
   同一个键显示三遍（members 里每个 mode 一条）。

**等价判据分三档**（可信度递减）：

| 情况 | 身份 | 可信度 |
|------|------|--------|
| 有 rhs | `rhs\|<右值>` | **严格** —— rhs 相同就是同一条命令 |
| Lua 回调 + 有 desc | `desc\|<描述>` | 弱 —— 同描述是同一功能（实测有效） |
| Lua 回调 + 无 desc | `lhs\|<键>` | 只能当独立题目，不聚合 |

第三档必须单独处理：若也按 desc 聚合，**所有无描述的键会合并成一道题**。

**最优解怎么选**：键数少 > 不用修饰键 > 不用 leader。
所以 `L` / `]b` 里选 `L`，`<Space>uZ` / `<Space>wm` 里选 `<Space>uZ`。

**最终 13 道多解命令**（对比旧手写表只有 4 组且错了 2 组）：

```
H         [rhs]  → [b          L          [rhs]  → ]b
<Up>      [rhs]  → k           <Down>     [rhs]  → j
<Space>`  [rhs]  → <Space>bb   <C-/>      [desc] → <Space>ft
<Space>   [desc] → <Space>ff   <Space>,   [desc] → <Space>fb
<Space>:  [desc] → <Space>sc   <Space>/   [desc] → <Space>sg
<Space>sl [desc] → <Space>xl   <Space>sq  [desc] → <Space>xq
<Space>uZ [desc] → <Space>wm
```

关卡概念（`LEVEL_NAMES` / `b.level`）是手编分类的产物，整个删掉，
所有按关卡统计/分组的地方改成按 which-key 分组：

| 文件 | 改动 |

| `components/stats-view.tsx` | 「关卡分布」→「分组分布」，显示 `inWhichKey` 覆盖率 |

| `app/stats/page.tsx` | tab `levels` → `groups` |
| `lib/matcher.ts` | 索引冲突时按**按键代价**取，不再按 level |

**⚠️ 顺手抓到一个静默失效的 bug**（`app/seq/page.tsx:35`）：

```ts
const TRAINABLE = BINDINGS.filter((b) => b.group !== "window");
```

which-key 里的真实分组名是 **`windows`（复数）**，而且窗口键大多落在
`ctrl-misc` / `leader-misc` 兜底桶里（`<C-H>`、`<Space>|`、`<Space>-`
都没有 which-key 分组）。所以这条过滤**从来没生效过** ——
不报错，只是窗口键一直在盲背池里出题，和可视化页面重复。

改成按 `desc` 认窗口导航（和 `/windows` 页面的判据一致）：

```ts

const TRAINABLE = BINDINGS.filter((b) => !WINDOW_NAV.test(b.desc));
```

全量 368 条 → 可练 347 条（排除 21 条窗口键）。

## 〇、先纠正我上一版的误判

我上一版把「题目区泄露答案」列为头号问题，**这个结论是错的**，至少是错位的。

那是站在「考试」范式下看的。而 Qwerty Learner 的跟打模式**本来就显示答案**——
显示 `abandon` 让你照着打，练的是手指走位，不是回忆拼写。答案可见不是 bug，
是这个范式的特征。

reflex 真正的问题是：**它是一个答题器，不是打字流。**

```
现在：  出题 → 你按 → 判分 → 等 1.5 秒 → 下一题        ← 断的
qwerty：题面 → 你连续打 → 逐键实时反馈 → 无缝下一题      ← 连续的
```

`advanceMs = 1500` 那个定时器、`按任意键继续`、`phase === "correct"` 的整块重绘——
这些都是「判分器」的零件。用户感觉「体验差」，差在**节奏被打断**：
每打一个序列就要停下来等一次，永远进不了流。

所以这次重做的主轴是**交互范式**，不是删答案、不是加键盘图。

## 一、qwerty 式的核心是什么

Qwerty Learner 能让人一练一小时，靠的是四件事：

| 要素 | 说明 | reflex 现状 |
|------|------|-------------|
| **连续流** | 打完一个词立刻是下一个，无停顿 | ✗ 每题等 1.5s |
| **逐键实时反馈** | 每敲一个字符立刻上色，错了当场看见 | ✗ 只在整串结束时判一次 |
| **实时数据** | 速度、正确率、连击，边打边跳 | ✗ 只有静态的「已掌握 n」 |
| **跟打 / 默写两种模式** | 前者显示答案练手感，后者隐藏练记忆 | ✗ 只有一种，且是后者 |

第五件是章节结构（词库选择 + 进度），reflex 已经有 9 个板块，**这部分可以直接沿用**。

## 二、映射到 reflex

### 2.1 一道题 = 一个「词」

Qwerty 里你打的是一个单词，reflex 里你打的是一个**键序列**。这个映射很自然：

| Qwerty | reflex |
|--------|--------|
| 单词 `abandon` | 键序列 `<Space>bd` |
| 释义 / 音标 | 命令描述「关闭当前 buffer」 |
| 逐字符上色 | 逐键上色 |
| 词库章节 | 板块（缓冲区 / 窗口 / 文本对象…） |
| KPM 速度 | 键/分 |
| 正确率 | 正确率 |

题库**完全不变**（你确认过：按 Vim 命令，保持现状题库）。
`lib/bufs.ts` / `lib/tabs.ts` / `lib/textobj.ts` 这些全部照用，改的是外面那层交互壳。

### 2.2 两种模式 = 跟打 / 默写

这是整个设计的支点，也正好解决「什么时候该显示答案」这个问题：

| | 跟打模式 | 默写模式 |
|---|---|---|
| 题面 | 描述 + **显示键序列** | 只给描述 |
| 你做什么 | 照着按 | 先回忆再按 |
| 练的是 | 手指走位、序列节奏 | 命令 → 键位的映射 |
| 计入进度 | 否 | 是 |
| 类比 | Qwerty 跟打 | Qwerty 默写 |

现在 6 个板块的 `AcceptList`（[buffers:111](../app/buffers/drill.tsx#L111) 等）
**不是要删，是要挪**——挪进跟打模式。它在默写模式里才是污染。

### 2.3 键盘图：不做

我从 git 里把 `faf66ae` 删掉的键盘图捞出来跑了一遍，26 个测试原样全绿，
跟现在的代码完全兼容，恢复成本是零。实现质量也确实高（ANSI 60% 真实布局、
Shift 派生符号、`<C-H>` 与 `<C-_>` 的 Shift 区别都处理对了）。

**但这次不恢复它**，理由就是你删它时说的「太吵/占地」，而且
qwerty 式练习器的屏幕是留给题面和数据的，不是留给键盘的。

代码在 `git show faf66ae:lib/keyboard.ts`，随时可以取回。真想要的话，
后续可以做成跟打模式里一个**默认收起**的「看图」小开关，但不在这一轮。

## 三、界面线框

### 3.1 主练习界面（跟打模式）

```
┌──────────────────────────────────────────────────┐
│ ← reflex        缓冲区 · 跟打                     │
├──────────────────────────────────────────────────┤
│  第 7/20 题   ▓▓▓▓▓▓░░░░░░░░  94%  138 键/分  ×12 │  ← 实时数据条
├──────────────────────────────────────────────────┤
│                                                  │
│              关闭当前 buffer，但不关窗口           │  ← 题面
│                                                  │
│           ⟨Space⟩   b   d                        │  ← 要按的序列
│            ▔▔▔▔▔▔   ▔   ▔                        │     已按的变绿
│                                                  │
│   ┌────────────────────────────────────────────┐ │
│   │ [ buffer 带子可视化 ]                       │ │  ← 题面的一部分,保留
│   │ ▸ a.txt  b.txt  c.txt                      │ │
```

### 3.3 按错的瞬间

```
│           ⟨Space⟩   b   x                        │
│            ▔▔▔▔▔▔   ▔   ▔                        │
│                        ✗                         │
│           正确的下一个键是 d                       │
```

**不重置整串**，停在错的那一位，提示正确的下一键，等你按对再继续。
理由是重置会打断节奏——而节奏正是这次要救的东西。
（另一种做法是像 Qwerty 那样标红继续往下打，但 Vim 序列按错后面基本无意义，
所以选「停住纠错」。）

## 四、引擎要改什么

### 4.1 逐键反馈

现有 `lib/drill.ts` 的 `classify(accept, buf)` 已经返回三态：

```ts
{ kind: "hit" | "prefix" | "none" }
```

**逐键上色是免费拿到的**：每按一个键后跑一次 classify，
`hit` / `prefix` → 这一键是绿的，`none` → 红的。

不需要新算法，只需要 `use-drill.ts` 在每次 keydown 后把「这一键对不对」暴露给 UI。
现在它只在 `hit` 时才有反馈，`prefix` 是静默收下的（[use-drill.ts:253-257](../lib/use-drill.ts#L253-L257)）。

### 4.2 去掉定时器

`advanceMs` 和 `setTimeout(() => setTaskIndex(...))`（[use-drill.ts:316](../lib/use-drill.ts#L316)）
整个删掉，改成命中即 `setTaskIndex(i => i + 1)`。

⚠️ 这里有个真实的坑：`task.accept` 是**多解法**的（`H` / `[b` / `<Space>bb` 都算对），
所以「打到第几键」不能只看一条序列。逐键上色要判的是
「当前缓冲是不是**某一条**解法的前缀」——`classify` 正好就是这个语义。

### 4.3 新增：会话

```
lib/drill/
  engine.ts    ← 现 lib/drill.ts,原样保留(纯函数 + 单测)
  session.ts   ← 新增:出题队列、轮次、计分、结算数据
  use-drill.ts ← 改:接 session,暴露 per-key 反馈
  ui.tsx       ← 改:拆成 题目区 / 数据条 / 结算屏
```

`session.ts` 是纯函数，配单测——延续现有 25 个测试的写法。
负责：一轮抽几题、记录每题对错与用时、算正确率/速度/连击、生成结算数据。

### 4.4 进度存储

沿用上一版的结论，合并成一个模型：

```ts
// reflex.srs.v1
type Item = {
  boardId: string;
  taskId: string;
  reps: number;      // 连续答对
  lapses: number;    // 累计答错
  ease: number;      // 难度因子
  dueAt: number;     // 下次复习时间
  lastAt: number;
  bestMs: number;    // 最快用时(速度榜)
};
```

现在 `lib/progress.ts` 的「连对3次=掌握」和 `lib/board-progress.ts` 的「做过」
被首页直接相加（[page.tsx:181-188](../app/page.tsx#L181-L188)），量纲不同不能加。
统一之后，跟打/默写分模式记（跟打不计入），错题本和复习队列才有可能。

### ⚠️ 一个关于「停住纠错」的设计取舍

旧版 `none` 分支会 `setBuf([])` —— 按错一个键，整串就没了，得从头再来。

新版**保留已按对的前缀**，只把错的那一键标红，等你接着按：

```
旧：<Space> b x  → 整串清空，从头开始
新：<Space> b x  → 保留 <Space> b，x 标红，接着按 d 就能完成
```

理由：Vim 序列按错之后，后面几个键基本没有意义
（`<Space>bd` 按成 `<Space>bx`，继续按 `d` 也不会变对），
所以不学 Qwerty 那样标红继续往下打，而是停在错处纠错。

### 阶段 4 已完成：跟打 / 默写双模式 + 提示分级

**新增 `lib/hints.ts`**（18 个测试）—— 提示分级与模式判定，纯函数。

#### 两种模式

| | 跟打（`drill`） | 默写（`recall`） |
|---|---|---|
| 题目区 | 直接显示全部键 | 空格子，自己回忆 |
| 练什么 | 手指走位、序列节奏 | 命令 → 键位的映射 |
| 计入熟练度 | **否** | **是**（且没用提示） |

模式记在 localStorage（`reflex.mode.v1`），默认**默写** —— 因为它计入进度。

#### 提示分四级（按 `?` 逐级上升）

```
0 级  什么都没有          ← 默认，先自己回忆
1 级  首键                ← 首键往往是最难回忆的那一步
2 级  首键 + 键数          ← 知道要走几步
3 级  全部解法            ← 放弃回忆，看答案
```

⚠️ **到顶不循环** —— 循环会让用户分不清按到第几级，而且到顶后再按一次
突然变回「什么都没有」，像是把帮助收回去了。

⚠️ **单键的题不给提示按钮** —— 给首键等于直接给答案，提示没有意义。
UI 用 `hintUseful()` 隐藏它，而不是给一个骗人的「提示」。

#### ⚠️⚠️ 最关键的一条：用过提示的题不算独立答对

`Summary` 新增 `independent` 字段，和 `correct` 分开：

- `correct` = 按键对了（含跟打模式照抄的、按提示抄的）
- `independent` = **真的记住了**（默写模式 + 没用提示）

没有这一条，「按提示抄一遍」会污染熟练度数据，复习队列就废了 ——
而且**不报错**，只是数据慢慢变脏。

`countsForProgress(mode, usedHint)` 和 `summarize().independent` 是同一套语义，
`tests/modes.test.ts` 里有一条测试专门盯「两套判据一致性」：

```ts
it("countsForProgress 和 summarize 的判据一致", () => {
  for (const mode of ["drill", "recall"]) {
    for (const usedHint of [false, true]) {
      // 两套算法必须给出同一个答案
    }
  }
});
```

#### `?` 键的两个坑

1. **必须在 `shouldTake` 之前判** —— `?` 不在本题解法的首键集合里
   （数据集里只有 `<Space>?` 这个键），`shouldTake` 会返回 false 直接放行，
   提示就永远按不出来。
2. **只在缓冲为空时接管** —— 序列按到一半时 `?` 可能是某条解法的续键。

#### 架构上的收敛

`KeySequence` 现在收 `shownKeys: (string | null)[]` ——
**「显示什么」由引擎算好，组件不需要知道模式**。
判据在 `lib/hints.ts`，有单测；组件只管渲染。

同时把 `/buffers` 从「自己手写的 SessionBar + SummaryScreen」统一到 `DrillFlow`，
6 个板块现在共用同一套外壳（数据条 + 模式条 + 结算屏）。

### ⚠️ 迁移时发现的一个真 bug：逐键反馈的过期记录

「停住纠错」的交互下同一个位置会被按多次：

```
按 <Space>  → feed = [{0, "<Space>", true}]
按 x（错）   → feed = [..., {1, "x", false}]       buf 还是 ["<Space>"]
按 b（对）   → feed = [..., {1, "x", false}, {1, "b", true}]
                                        ↑ 同一位置两条
```

UI 用 `find()` 取第一条，于是显示**过期的** `x`（红色）——
用户明明改对了，界面还在报错，而且**不抛异常**。

修法：`pushFeed` 在位置 N 按键时先删掉 `index >= N` 的旧记录。
这个 bug 在 6 个板块里都存在，一起修了。

### 阶段 6 的另一半：统一进度模型

`/seq` 迁到公共引擎后写的是 `reflex.board.v1`，而首页还在读
`reflex.progress.v1` —— **进度直接断裂**（在 `/seq` 练的首页看不见）。

原来有两套存储，量纲完全不同：

| 存储 | 形状 | 语义 |
|------|------|------|
| `reflex.progress.v1` | `{seen, correct, streak, lastAt}` | 「连对 3 次 = 掌握」 |
| `reflex.board.v1` | `string[]` 已做过的题号 | 「做过」 |

首页把两者**直接相加**成一个总进度条 ——「做过 3 道题」和
「连续答对 3 次」被当成同一件事。

新增 `lib/srs.ts`（25 个测试）合并成一个模型：

```ts
type Item = {
  board: string;       // 属于哪个板块（各板块 taskId 体系不同，必须标）
  seen, correct;
  independent: number; // 其中「独立答对」—— 判断学会的依据
  streak, lapses;
  lastAt, dueAt;       // 时间维度 → 复习队列
  bestMs;
};
```

**间隔重复**：连对越多复习越远（1 → 3 → 7 → 16 → 35 天），
答错**立刻回插**（`dueAt = now`）。

⚠️ 只有**独立答对**才推后间隔 —— 按提示抄对的不该让复习变远，
否则越抄越久不复习，正好反了。

⚠️ 每个 item 带 `board` 标记 —— 各板块的 taskId 体系不同
（`/buffers` 是 `L#0`，`/seq` 是 `n|L`），而进度是全局一张表。
没有这个标记，首页就没法按板块统计。

**迁移**：`load()` 会读旧的两个 key 转成新格式，**不删旧数据**（可反悔）。
旧 `progress` 没有 independent 概念，保守地按 `min(correct, streak)` 估；
旧 `board` 的 id 形如 `L#0`，和新的 `n|L` 对不上的就跳过 ——
宁可少几条，也不硬塞一个错的映射。

首页现在能显示「该复习 n 条」—— 这是统一模型才做得到的事。

### ⚠️ 顺手修掉的一个语义 bug

`weakest()`（弱项排序）第一版只按错率排，**没排除零错误的题** ——
于是「连对 3 次已掌握」的题也被选进弱项。界面上会变成
「你的弱项：<一个你已经掌握了的键>」。加了 `lapses > 0` 过滤。

### 阶段 6 补完：跨板块 id 统一 + 两个维度说清楚

#### ⚠️ 同一条命令被记成两条进度

进度是**全局一张表**（`lib/srs.ts`），key 是 task id。
但各板块原来用**本地 id**：

```
/buffers  →  "L#0"    （题库下标）
/tabs     →  "<Tab>d#1"
/seq      →  "n|L"    （COMMANDS 的全局 id）
```

于是在 `/seq` 练过「下一个 buffer」再去 `/buffers`，那题还是「没见过」——
**同一条命令两份进度**，复习队列重复出题，首页掌握数虚高。

新增 `lib/task-id.ts`：以 `COMMANDS` 的 id（`mode|lhs`）为唯一真源。
能映射的 4 个板块（buffers / tabs / files / ui）统一用它，
查 `taskIdOf("buffers", "L")` 和 `taskIdOf("seq", "L")` 都是 `n|L`。

**但不能一刀切** —— 实测有三类映射不过去：

| 板块 | 原因 |
|------|------|
| text | `diw` 是 Vim 内建文本对象，不在 `nvim_get_keymap` 里 |
| diagnostics | `gr*` 是 buffer-local 映射，不在全局表里 |
| windows-hydra | hydra 面板键只在 `<Space><Space>` 之后才存在 |

这类用 `板块:本地key`（带前缀防跨板块撞车）。

⚠️ `/buffers` 里有两道题 key 都是 `L`（故意考「从末尾切回第一个会绕回」），
起始状态不同、是两道题。所以 `taskIdOf` 支持 `suffix`，
**只在真的有重复 key 时才用** —— 滥用会让跨板块共享失效。

#### 口径：两个维度，不是两个口径

一开始我把它当成「口径不一致的 bug」，查下去发现是**两个正交的维度**：

| 维度 | 分母 | 回答的问题 | 在哪 |
|------|------|-----------|------|
| **板块** | 题库长度 | 我还差多少题要练 | 首页 + `/stats` 新增的「按板块」 |
| **which-key 分组** | 数据集条数 | 数据集本身长什么样 | `/stats` 的「分组分布」 |

`L` 在板块维度属于「缓冲区」（它是练 buffer 的题），
在分组维度属于「裸键」（它在 which-key 里没有 `<Space>` 前缀）。两个都对。

**真正要统一的是同一维度内的数字**：

- 板块定义抽到 `lib/boards.ts`（唯一一份），首页和 `/stats` 都从这里读
- 两处都用 `SRS.byBoard()` 统计 —— 同一个函数，数字必然一致
- `/stats` 新增「按板块」tab，用同一个入口

#### ⚠️ 改 id 时踩到的 500

改完 id 后 `/ui` 整页 500：`Cannot read properties of undefined (reading 'group')`。

原因是页面里还有 `UI_TOGGLES.find((x) => x.key === d.task.id)` ——
`d.task.id` 现在是全局 id（`n|<Space>uL`），而 `x.key` 是 `uL`，
`find` 返回 `undefined`，后面读 `.group` 就炸了。

改成用 `TASK_OF` 反查。**同类 bug 排查过一遍**：
其余板块都用的 map 反查，只有这一处是 `.find` 直接比 key。

新增 `tests/cross-board.test.ts` 守住「注册表里的 board id
必须能在代码里找到对应的 `boardId`」—— 这条如果对不上，
首页统计会**永远显示 0**，而且不报错。

### 覆盖率审计（「按键覆盖全覆盖了吗」）

用户问「总觉得有漏掉的」。查下来有两层含义，**都不是同一个问题**：

#### 第一层：漏解法（已修）

同一条命令的其它键没被认出来。旧手写表既多又少 ——
`<Space>bb` 被错当成 `L` 的等价解，而 `j`/`<Down>`、`k`/`<Up>`
两组真等价键**完全没收录**。按 `rhs` 聚合后修好了。

#### 第二层：漏键位（查完：没有真缺口）

新增 `tests/coverage.test.ts` 做系统审计：

```
数据源 387 条
  → 过滤 19（<Plug> / termcode / F 键 / 空）
  → 唯一键位 367
  → 全部进 RAW（零丢失）
  → 聚合出 260 道命令
```

其中 **95 条没有独立命令**，但原因都正当：

| 原因 | 条数 | 说明 |
|------|------|------|
| 空 desc | 8 | 插件没上报描述，无法出题 |
| 同 desc 已在别的 mode 出题 | 87 | 跨 mode 合并，避免同一命令出多道题 |

#### ⚠️ 特别澄清：「x 模式 0 条出题」不是缺口

审计发现 `x` 模式 43 条键**一条都没出题**，看着很吓人。查下来：

- nvim 里 `v` / `x` / `s` 是 Visual 的三种子模式，**同一批映射会重复注册**
- **没有任何键是 x/s/t 独有的** —— 实测（`coverage.test.ts` 里那条断言）

所以练 `v` 就等于练 `x`。同理 `c` 模式的 11 条缺口全是 auto-pairs
（`Open action for "()" pair`）和 MiniPairs —— 那是自动配对行为，不是要背的键位。
`o` 模式的缺口是 `a`/`i`/`al`/`in` 这些文本对象前缀，由 `/text` 页面覆盖。

**结论：覆盖率没有真缺口。** 那些「看起来没练到」的键，要么翻不了、
要么在别的 mode 出了题、要么由专门的页面覆盖。

### `/seq` 去掉按钮墙

`/seq` 原来用 `TaskBar`（每道题一个按钮）。leader 形态下有 131 条 ——
那是**一面墙的按钮**，把题目区和可视化全挤到屏幕外，
而它的唯一作用是「跳到某道题」。131 个按钮既扫不过来、也想不出该点哪个。

改成一个轻量控制行：`跳过 / 重来 / 清进度`，

### 跨页面去重（/seq 不再重复出题）

`/seq` 的描述是「**其余**全部键位」，但实测它和专门页面**重复了 70 条**：

```
<Space>f*   文件查找    10 条
```

判据放进 `lib/boards.ts` 的 `boardCoveredIds()`：每个板块声明自己拥有哪些键，
`/seq` 读它过滤。池子 **243 → 173**。

⚠️ 踩到的坑：`/windows` 的题是**三段式** `<Space>wX`，

把**全局**的 `H`（上一个 buffer）和 `>`（缩进）也标记成「被覆盖」。

### 搜索跳转可视化（新增 `/search` 板块）

新增 `lib/search-nav.ts`（24 个测试）+ `SearchNavView` 组件 + `/search` 页面。

`n` / `N` 看着最简单，但实测本机映射是**方向感知**的：

```vim
n → 'Nn'[v:searchforward].'zv'
N → 'nN'[v:searchforward].'zv'
```

| 怎么搜的 | `n` | `N` |
|---------|-----|-----|
| `/foo` | 往后 | 往前 |
| `?foo` | **往前** | **往后** |

用 `?` 倒着搜完再按 `n` 是往回走 —— 光看 desc「Next Search Result」
完全看不出来。所以题库里**故意加了两道反向搜索的题**，
普通练习只会从正向开始，永远练不到这个点。

第二件容易记错的：**`<Esc>` 只清高亮、不清搜索寄存器**
（LazyVim 映射成 `:nohlsearch`），清完再按 `n` 还能跳。

### ⚠️⚠️ 实测推翻了两个「凭直觉写的」行为

做 `]q`/`[q` 时顺手把 `]d` 的行为也实测了一遍 —— **发现我写错了**。

#### 错误 1：`]d` 到头**会绕回**，我写成了「不动」

`]d` 在本机的 rhs 是**空的**（Lua 回调），`nvim_get_keymap` 看不出行为。
我按 Vim 手册的直觉建模成「到末尾不动」，**还为它写了注释和测试**，
声称「这和 `:cnext` 会绕回是两回事」。

实测（`scripts/probe-nav.lua`）：

```
诊断在第 3、7 行，从第 1 行连按 ]d：
  第 1 次 → 第 3 行
  第 2 次 → 第 7 行
  第 3 次 → 第 3 行   ← 绕回了！
```

**`]d` 和 `:cnext` 的行为是一样的。** 我原来写反了，
而那条「证明它不绕回」的测试把**错的**行为锁住了。

#### 错误 2：`]q` 和 `]d` 行为**不一样**

差点又犯一次同样的错 —— 我打算直接把 `]d` 的模型套到 `]q` 上
（都是「在列表里前后走」）。实测（`scripts/probe-qf.lua`）：

| | `]d`（诊断） | `]q`（quickfix） |
|---|---|---|
| 到头 | **绕回** | **停住**（报 `E553: No more items`） |

```
quickfix 在第 2、5、8 行：
  连按 ]q → 5, 8, 8, 8, 8    ← 停住
  连按 [q → 5, 2, 2, 2, 2    ← 停住
```

这也解释了为什么用户会觉得两族「手感不一样」。

#### 教训

`lib/provenance.ts` 里那条又应验了一次：**探针没验证过 → 结论不成立**。

- `]d` 的 rhs 为空 = **看不出行为**，必须真的按一遍
- 「两族看起来同构」**不是**可以共用一个模型理由

两个探针都放进 `scripts/`（`probe-nav.lua` / `probe-qf.lua`），
输出存在 `data/probe-*.txt`，可复现：


### `/seq` 改成 which-key 分类

**起因**：`/seq` 原来用「按键形态」分组（leader / ctrl / brackets / bare）。
那个分法只回答「这键长什么样」，而用户脑子里是「这键干什么用」——
which-key 面板里看到的正是后者。

现在真分组直接用 which-key 的 `group`，兜底键合成「其它」：

```
搜索 32 · Git 14 · 上一个 14 · 下一个 13 · 跳转 8
代码/LSP 5 · 文件查找 5 · 退出/会话 5 · 性能分析 3
缓冲区 1 · 诊断/quickfix 1 · 其它 34 · 全部 135
```

兜底键（63 条）原来分成 insert / visual / ctrl-misc / leader-misc /
bare / other / operator 七桶，七个小桶各自成按钮意义不大，
合成「其它」更好用 —— 它们本来就是「which-key 没管的那批」。

#### ⚠️ 修掉一个真 bug：`COMMANDS` 漏了 `inWhichKey` 字段

想按 which-key 分类时发现：`c.inWhichKey` **永远是 `undefined`** ——
173 条**全被判成兜底桶**，包括本该是真分组的 `search` / `git` / `goto`。

根因：我建 `COMMANDS` 时没把 `inWhichKey` / `wkGroup` 带过去
（`RAW` 上有 208 条是真分组，`COMMANDS` 上是 0）。

#### ⚠️ 修掉一个聚合漏洞：matchit 的 mode 变体

`%` / `g%` / `[%` / `]%` 各出了 **3 道题**（在 n/v/o 各注册一条），
因为 matchit 把同一件事按 mode 桥接到不同的 `<Plug>` 上：

```
%  n  <Plug>(MatchitNormalForward)
%  v  <Plug>(MatchitVisualForward)
%  o  <Plug>(MatchitOperationForward)
```

三条 rhs 不同 → 按原样聚合不会合并。但它们对用户就是
「跳到配对的括号」**一件事**。

所以聚合时把 `(Matchit|Textobj|Repeat)(Normal|Visual|Operation|Select|Op)`
这类**模式前缀**归一化掉。模式信息不丢 —— 它记在 `modes` 数组里。

命令数 **260 → 252**。

### `/windows` 的 jump / build 已并入（最后一块技术债）

原来 `/windows` 有**三套**独立实现：hydra（已用公共引擎）、
jump（`drill.tsx` 297 行）、build（`split.tsx` 413 行）。

#### ⚠️ 难点：它们是「目标判定」，不是「序列匹配」

引擎原来的模型是「一题 = 一条固定键序列，命中 `accept` 即结算翻页」。
但 jump / build 是**另一种形态**：

| | 序列匹配（其余 8 个板块） | 终态判定（jump / build） |
|---|---|---|
| 一题几步 | 固定 1~3 键 | **不固定** |
| 正确答案 | 预先枚举的几条 | **取决于当前状态**，路径不唯一 |
| 判据 | 键序列相等 | **状态是否达标** |

硬塞进 `accept` 不行：jump 里从 A 到 B 有几十条等价路径，枚举不完；
而且枚举了也会「第一步就 hit 结算」，走不了多步。

#### 解法：给引擎加 `isSolved` 钩子

```
每按一键 → apply 推进状态 → isSolved(新状态) 判「到了吗」
         → 没到就继续走，到了才结算翻页
```

还加了 `firstKeysOf`（接管范围由板块自己给，因为合法性取决于当前状态）。

⚠️ 终态模式也要支持**多键序列**（build 的 `<Space>|`）——
分四种情况：完整动作 / 序列开头 / 序列后续 / 走不动。

#### 同化抓到两个真 bug

**1. build 的示范解法照到页面上会卡住**

四宫格的目标形状来自 `run([{dir:"v"},{go:"l"},{dir:"h"}])`，
但 `run()` 的语义是「分屏后焦点**不跟进**」，而**页面的实际按键**
是「焦点**跟到新窗口**」（和原实现一致）。

两者不一致 → 题库里写的 `[{dir:"v"},{go:"l"},{dir:"h"}]`
用户照着按**会卡住**：竖切后焦点已经在新窗口，再按 `<C-L>`
右边没有窗口。穷举验证后改成 `[{dir:"v"},{dir:"h"}]`。

**2. `<Space>w` 中间态不能返回 NO_EFFECT**

`<Space>wd` 是三键序列。我第一版让 `apply(["<Space>","w"])`
返回 NO_EFFECT，引擎当「这一键走不动」报错并**清空缓冲** →
紧接着的 `d` 到达时序列已经没了 → 关窗口永远按不出来。

修法：中间态**原样返回状态**（表示「收到了，继续等」）。

### 窗口缩放可视化（`/windows` 的第四个模式）

新增 `lib/split.ts` 的 `resizeByCells()` + `canResize()` +
`app/windows/resize.tsx`（11 个测试）。

#### ⚠️⚠️ 实测又推翻了书面结论（第六次）

早先 `lib/keys.ts` 里写过（后来清理时删了）：

> 书 9.3.5 说裸按 `<C-Up>` 只挪一行/一列，真实场景要 `20<C-Up>`

**实测两条都不对**（探针 `scripts/probe-resize.lua`）：

```
<C-Right> 的 rhs = <Cmd>vertical resize +2<CR>   ← 每次挪 2 列
按 10<C-Right> → 也只挪 2 列                      ← 计数被忽略
按 30<C-Right> → 还是只挪 2 列
```

| 按键 | 宽度变化 |
|------|---------|
| `<C-Right>` | 39 → 37（挪 2）|
| `10<C-Right>` | 37 → 35（**也是 2**）|
| `30<C-Right>` | 35 → 33（**还是 2**）|

原因：本机 LazyVim 把步长**硬编码在 rhs 里**（`resize +2`），
不像 Vim 内建的 `<C-w>>` 那样吃计数。所以书里那条
「加计数来多挪」**在本机不成立**。想挪更多得手打
`:vertical resize +10`。

#### ⚠️ 顺带修掉一处数据错误

`scripts/build-dataset.mjs` 里的原生等价原来写的是 `:resize ±1`
（凭印象），实测是 **`±2`**。数据集里的 rhs 字节码不会骗人：

```
<C-Right>  rhs="<Cmd>vertical resize +2<CR>"
<C-Down>   rhs="<Cmd>resize -2<CR>"
```

#### 为什么不能用 `lib/split.ts` 原来的 `resize()`

`resize()` 按 **ratio 步进 0.1**，转成实际列数取决于屏宽
（80 列屏上一步 = 8 列）。而本机是**固定 2 列** ——
两者语义不同，所以新增了 `resizeByCells()` 做换算。

新增测试专门守这条：**不同屏宽（60/80/120/200 列）下挪的列数一样**。
